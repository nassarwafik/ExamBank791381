# Phase F4 — Project exam form: student images, server side

## Problem

The exam forms ask the student for evidence from their own project: a screenshot of the cover, of a table's design, of a
web-service test, of the running site (14 image questions in 883589, 13 in 794589, and one code question in 794589 that
asks for images beside its text). Since F2 those questions are shown and take no answer («يُفتح لاحقًا»), and never block a
submit. The owner asked for the form to include «إرفاق صور من المشروع», decided in F1 that images are allowed (owner
decision 3), and chose this phase on 2026-11-14.

This phase is the **server side**, as F2 and F3 were: where an image is stored, what it goes through, who may read it,
and what it means for a submit. The student's upload control, the teacher's switch and the display of the images are the
next phase (F4-UI). Until then no screen can switch image answers on, so nothing changes for any user.

## Scope

| In this phase | Not in this phase |
|---|---|
| A per-class switch: image answers on | The teacher's control that sends the switch — F4-UI |
| Attach one image, remove one image (student) | The student's upload control and thumbnails — F4-UI |
| Read one image: the student who owns it; the teacher of the class | Showing the images in the teacher's review page — F3-UI / F4-UI |
| Image questions count for progress and submit where images are on | Files (`.pkt`, the book) — F5 |
| A second output profile of the platform's one image pipeline | Deleting a class's or a leaving student's images (no deletion without the owner's plan) |

## Decisions taken in this phase

| Question | Decision | Why |
|---|---|---|
| Do image questions become answerable for every class at once? | **No.** A class's image answers are off until its teacher switches them on (`imageAnswers: true` on `examForm.open`). | A class already filling the form was told image questions do not block a submit; nothing changes under it silently. It is also the gate that keeps this phase unreachable until the screens exist. |
| Can the switch be turned off again? | **No** (`409 IMAGES_FROZEN`). It can be switched on at the first open or by any later open. | A class whose students attached images cannot lose the input or have required questions disappear. |
| Where is an image referenced? | Inside the answer of its question: `answers[questionId].images = [{ id, width, height, bytes, addedAt }]`. | One answer per question stays the model; the teacher's review read (F3) carries the references with the answers, unchanged. |
| Does attaching an image advance `revision`? | **No.** | `revision` guards a page from overwriting newer answers. Adding or removing one image overwrites nothing, so a page that missed it has nothing to undo, and a text save is never refused because a photo was attached meanwhile. |
| What happens to the blob when the student removes an image? | The reference is removed (CAS), then the blob is deleted, best effort. | An unreferenced image has no reader. A failed delete leaves a blob no route can serve, never a broken reference. |
| How many, how large? | Per question, the form's own `images.max` (at most 6). Upload at most 6 MB; stored as WebP inside a 1600 px box. | A screenshot's text must stay readable; a phone photo of the physical network must fit. |

Open for the owner (F4-UI): whether the teacher's control switches images on by default for a new class.

## Storage

| Document | Blob | Shape |
|---|---|---|
| Class form (F2) | `platform/project-exam-forms/<code>/classes/<classId>.json` | gains `imageAnswers: true`, `imageAnswersAt`, `imageAnswersBy` — only once switched on (absent otherwise, so a form opened before F4 is byte-for-byte what it was) |
| Student answers (F2) | `…/answers/<classId>/<studentId>.json` | an answer may carry `images: [{ id, width, height, bytes, addedAt }]` |
| Image (new) | `platform/project-exam-forms/<code>/images/<classId>/<studentId>/<imageId>.webp` | one immutable WebP per attached image; `imageId` is 24 hex characters generated by the server |

Images live outside the `answers/` prefix, which the class list reads as JSON documents. No existing document is moved,
rewritten or deleted.

## The image pipeline

An upload goes through the platform's **one** image-normalization service (`api/src/lib/profile-image.js`), the path every
personal photo already takes; there is no second, weaker one. This phase adds an output profile to it, nothing else:

1. the transport and the raw upload are bounded **before** decoding (6 MB; `413 TOO_LARGE`);
2. the real bytes are sniffed — only JPEG, PNG and WebP rasters; SVG, GIF, PDF, HTML, text and arbitrary binary are refused
   whatever the declared type says (`400 UNSUPPORTED`);
3. the image is decoded (a file that only starts with a raster signature fails here: `400 UNDECODABLE`), with the 40 MP
   decompression-bomb guard;
4. EXIF orientation is applied, the image is fitted **inside** 1600 × 1600 (never enlarged, never cropped);
5. it is re-encoded to WebP — a freshly generated raster, so EXIF / GPS / device / ICC metadata never survive.

The personal-photo and logo profiles are unchanged (512 px, 3 MB); a test pins that.

## API

**Teacher** — `api/src/functions/project-tracker.js`, behind its existing dispatch (`GET` → `projects.tracker.view`, every
action → `projects.tracker.manage`; the teacher's own class, enrolled in the project; an archived class refuses every
action). No new route, no new capability.

| Request | Result |
|---|---|
| `action=examForm.open` `{ imageAnswers: true }` | switches the class's image answers on, at the first open or later. `changed: true` and an audit record `project.exam_form.open` with `imageAnswers: true` when the switch moved. `false` on a class that has them on: `409 IMAGES_FROZEN`. A non-boolean: `400`. Absent: the class stays as it is. |
| `GET resource=exam-form` | `examForm.imageAnswers: true` once on (absent while off) |
| `GET resource=exam-form-image&studentId=&imageId=` | `image/webp`. The student must be a member of the class and the image must be referenced by that student's answers; anything else is `404`. |

**Student** — `api/src/functions/student-project-exam-form.js`. The student and the class come only from the session.

| Request | Result |
|---|---|
| `POST { projectCode, action: "addImage", questionId, dataUrl }` | sanitizes and stores the image, references it from the answer; the form body plus `image: { id, width, height, bytes }` |
| `POST { projectCode, action: "removeImage", questionId, imageId }` | removes the reference and the blob; `changed: false` when the image is not there (a repeat is harmless) |
| `GET ?projectCode=&image=<imageId>` | `image/webp`, the student's **own** image only (`404` otherwise). Readable in an archived class too (its record). |
| `GET ?projectCode=` | `deferredKinds` is `["file"]` where images are on, `["image", "file"]` otherwise; `progress` counts image questions accordingly |

Refusals, each writing nothing and storing no blob: images off for the class `400 KIND_NOT_AVAILABLE`; a question that is
not in the class's form (unknown or hidden) `400 UNKNOWN_QUESTION`; a question that takes no image `400 NO_IMAGES_HERE`; the
question is full `409 IMAGE_LIMIT`; closed `409 FORM_CLOSED`; submitted `409 FORM_SUBMITTED`; approved `409 FORM_APPROVED`;
archived class `403`; form never opened `404 FORM_NOT_OPENED`; a draft save that names an image question
`400 IMAGE_VIA_UPLOAD`. A returned form takes images again, like its other answers.

Both image reads answer with `Cache-Control: private`, `X-Content-Type-Options: nosniff` and `Content-Disposition: inline`.

## Answer rules with images on

| Question | Counts as answered when |
|---|---|
| `image` | it holds at least `images.min` images, and at least one (an optional question with nothing attached is not «answered») |
| a text / code / table question that asks for images | its text / rows are answered **and** it holds at least `images.min` images |
| every other kind | as in F2 |

A required image question therefore blocks a submit (`400 FORM_INCOMPLETE`, listed in `missing`) until its images are
attached. With images off every rule is F2's: image questions are deferred, never counted, never blocking.

## Safety

- **The server decides.** A reference is written only by the server, with an id it generated for a blob it stored. A draft
  save rebuilds each answer from the fields its question allows, so an `images` list sent by a client is dropped, and an
  image question is refused outright. A draft never loses the stored images of a question either.
- **Protected content never bypasses the API.** An image is not a static asset and has no public URL. It is served only
  when the answers document of that student references it: to the student (the session's own identity) and to the teacher
  of the class (capability, tenancy, class enrolment, membership). The id alone is never enough: the blob name is built
  from the class and the student too, and an existing blob that is no longer referenced is not served.
- **Sanitized, always.** Nothing a student uploads is stored as sent: only the re-encoded WebP exists. No SVG, no script,
  no metadata.
- **Fail closed.** Order of the attach: sanitize → store the blob → reference it in one CAS round. When the round refuses
  (full question, form closed or submitted meanwhile, storage conflict) the blob just written is removed, and the answers
  are untouched.
- **Grading safety.** Nothing here produces a mark. An image question that was never switched on is «not asked», not a
  missing answer; a failed upload is an error the student sees, never an empty answer stored.
- **Identity.** A body `studentId` / `classId` is never read on the student route.
- **No new infrastructure.** Images are blobs in the existing container; processing is the existing `sharp` pipeline.
- **Nothing is deleted or migrated.** A class reset, a closed form and a student who leaves the class keep their images;
  a former member's images are no longer served through the class (the same policy as F3's class list).

no image, unknown and hidden questions; closed / submitted / approved / archived / returned; identity from the session;

Fail-first is not applicable: new behaviour, no defect fixed.

## Known limits

- No user can reach any of this until F4-UI: no screen sends `imageAnswers`, attaches an image or shows one.
- The merged student page (F2-UI) does not know how to answer an image question. A class whose images were switched on
  through the API before F4-UI ships would show required questions with no input; nothing in the product can do that
  today, and F4-UI must ship the input together with the switch.
- There is no quota beyond the per-question maximum; a student's stored images are bounded by the form (the sum of its
  maxima), and each stored image by the 1600 px box.
- Images are processed in the request; a 6 MB upload is decoded in memory by the Functions host.
